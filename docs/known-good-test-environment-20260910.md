# Known-Good Test Environment

Status: milestone checkpoint, 2026-09-10. This is the known-good Mudos test
environment on CachyOS. It is not a BC-250 deployment recipe and must not be
used to infer hardware-specific values for the real Lulu appliance.

## Milestone Result

- Three Xbox 360 wireless controllers were presented by InputPlumber as
  independent virtual Xbox gamepads.
- Mario Kart Wii was manually validated with three simultaneous players.
  Each controller drove its assigned player only; no duplicate or dead slot
  was observed.
- Guide was manually validated from P1, P2, and P3. Each controller opened
  and navigated the Mudos Guide overlay.
- Guide subscription is dynamic. The shell discovers each live composite's
  `DbusDevices`, subscribes to the actual target path, associates events with
  their composite owner, and removes the subscription when that composite
  disappears.
- Successful provider/controller mappings are frozen at this checkpoint.
- RetroArch lifecycle, Steam three-controller visibility, and full reconnect
  validation were intentionally not resumed after Guide passed.

## Controller Contract

InputPlumber currently exposes composites through the manager's
`GamepadOrder`. Runtime target numbering is not a physical identity.

Validated non-sequential evidence:

| Logical player | Composite | Gamepad target | D-Bus target |
| --- | --- | --- | --- |
| P1 | `CompositeDevice0` | `gamepad0` | `dbus0` |
| P2 | `CompositeDevice2` | `gamepad2` | `dbus2` |
| P3 | `CompositeDevice1` | `gamepad1` | `dbus1` |

The successful Dolphin integration used GameCube Ports 1, 2, and 3 with the
known-good stock SDL Gamepad semantics. The provider profile follows the
logical-player-to-current-target mapping; it does not assume numeric target
names identify players.

After a fresh session restart, the current runtime may assign P1, P2, and P3
sequentially. That is expected runtime state, not a changed contract.

## Generated By Mudos

Mudos generates or updates the following under the `lulu` home directory:

- `/var/lib/lulu/.local/share/lulu/catalogue.sqlite3`.
- Artwork cache and generated application/catalogue metadata.
- `/var/lib/lulu/.config/dolphin-emu/GCPadNew.ini` and the relevant Dolphin
  `Dolphin.ini` controller-port values.
- `/var/lib/lulu/.config/PCSX2/inis/PCSX2.ini` native SDL controller sections.
- Temporary per-launch RetroArch append configurations under the runtime
  directory.
- Runtime logs, save data, shader/cache data, and other provider state.

These files are mutable state and should not be copied as the source of the
controller contract. Reprovision them from the repository and current live
InputPlumber discovery.

## System Provisioning

Host-owned files and settings required by this test environment:

- `/etc/systemd/system/lulu.target`.
- `/etc/systemd/system/lulu-session@.service`.
- `/etc/systemd/system/lulu-consoled.service`.
- `/etc/systemd/system/inputplumber.service.d/restart.conf`.
- `/etc/inputplumber/devices.d/lulu-composite.yaml`.
- `/etc/pam.d/lulu-session`.
- `/etc/lulu/presentation.conf`.
- `/etc/lulu/steamgriddb.env` is a host secret and must be recreated
  separately, never committed.
- `seatd.service` runs with the `seat` group and is required by the session.
- `inputplumber.service` is enabled and uses the packaged daemon with the
  restart drop-in.

The active session uses VT 2, UID/GID 958, `DISPLAY=:0`, Gamescope output
connector `HDMI-A-1`, and `/run/user/958` for the user D-Bus and PipeWire
runtime. The session service sets `PYTHONPATH=/opt/lulu/lib` and
`LULU_NATIVE_CONTROLLER=1`.

No custom Xbox-specific udev rule was found outside the package-provided
InputPlumber and Steam rules. Physical controller access is provided by the
`xpad` driver and the seat/device permissions.

## `/opt/lulu` Deployment

The active services load Python modules from `/opt/lulu/lib` and binaries and
assets from `/opt/lulu/bin`, `/opt/lulu/config`, `/opt/lulu/ui`, and
`/opt/lulu/scripts`. The deployment was synchronized for this checkpoint,
including:

- Python controller/session/consoled modules.
- `lulu-shell`, rebuilt from `native/lulu-shell.cpp`.
- Existing Mudos UI, helper, scripts, profiles, and RetroArch autoconfig.

The deployment is manually installed, not produced by an installed package.
Fresh reproduction must build and install it with the repository scripts or an
equivalent controlled install procedure, then install the systemd templates.

## InputPlumber

The host device definition is a non-persistent, one-source-per-composite
topology:

- Vendor/product match: `045e:02a1`.
- `maximum_sources: 1`.
- `auto_manage: true`, `persist: false`.
- Targets: gamepad, keyboard, and mouse.

At the final audit, three composites were present, each had
`InterceptMode=1`, `ProfileName=Default`, and one discovered D-Bus target.
The physical receiver reported the same `PersistentId=045e_0291` for all
three controllers, so persistent physical identity and guaranteed reconnect
slot recovery are not available.

## Provider And Emulator Provisioning

- Dolphin is installed as `dolphin-emu`; the Wii ROM is an RVZ under
  `/var/lib/lulu/roms/wii`.
- PCSX2 is installed as the foreign/AUR `pcsx2` package; PS2 BIOS and ROMs are
  under `/var/lib/lulu/bios/ps2` and `/var/lib/lulu/roms/ps2`.
- RetroArch is installed with Nestopia and Genesis Plus GX cores. The existing
  P1 RetroArch configuration is retained; the multiplayer/reconnect behavior
  was not promoted to a validated milestone result.
- Dolphin uses the installed stock SDL Gamepad semantic names and mappings,
  with per-player current SDL target selection.
- PCSX2 uses native `SDL-N` sections generated in its INI.
- Mudos supplies the RetroArch autoconfig directory and per-launch append
  configuration without changing the persistent P1 configuration.

## Remaining Issues

- Reconnect behavior has been observed to recreate a composite and append it
  in `GamepadOrder`; the receiver exposes no unique physical identity, so
  deterministic original-player recovery is not guaranteed.
- RetroArch multiplayer mapping and reconnect behavior remain unvalidated.
- Steam visibility of three distinct Mudos virtual controllers remains
  unvalidated.
- The full Python test suite retains one unrelated fixture expectation failure:
  `runtime-missing` versus `bios-missing`.
- The deployment is not yet packaged as a reproducible CachyOS artifact.
- No BC-250-specific hardware, display, receiver, firmware, thermal, or
  production provisioning validation has been performed.

## Reproduction Boundary

This checkpoint is the stopping point for test-environment feature work. The
next task is a separate migration design for safely reproducing the required
repository, system, deployment, and user-data boundaries on real Lulu
hardware. Do not deploy this checkpoint to the BC-250 without that design.
